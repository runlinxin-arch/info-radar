## 一、先处理线上事故：隧道 QUIC 失效导致全站 502

### 现象

评审过程中（23:00 前后）`https://inforadar.xin/` **返回 502**，`/manifest.json`、`/about`、`/api/status` 等路径全部 502，响应体 16 字节 `error code: 502`。
（注：`/robots.txt`、`/favicon.ico` 一直是应用层返回的 **404 application/json**，与本次 502 是两回事。）

### 根因（已定位并验证）

不是应用挂了 —— 本地 `127.0.0.1:7100` 一直是好的。问题在隧道：

```
{"level":"error","error":"failed to dial to edge with quic: timeout: no recent network activity",
 "message":"Failed to dial a quic connection"}
```

cloudflared 默认用 **QUIC over UDP 7844** 连 Cloudflare 边缘。这台机器所在的网络在干扰 UDP，导致 cloudflared 拨号超时，**隧道没有任何活跃连接**（`cloudflared tunnel info` 明确报 `does not have any active connection`），CF 边缘自然只能回 502。

同一份 cloudflared 的 precheck 结果很说明问题：

```
UDP Connectivity  ... status:"pass"   details:"QUIC connection successful"
TCP Connectivity  ... status:"pass"   details:"HTTP/2 connection successful"
precheck complete  hard_fail:false    suggested_protocol:"http2"   <== 它在建议降级
```

### 修复（已实施）

给 `C:\Users\xinru\.cloudflared\config.yml` 增加一行，强制走 TCP：

```yaml
protocol: http2
```

改完后立刻注册上 4 条连接，公网恢复：

```
CONNECTOR ID                         CREATED                    EDGE
b17085a3-ca54-49c5-bd35-5cd80b22d336 2026-09-27T15:12:40Z       2xlax01, 1xlax07, 1xlax10

公网连续 3 次: HTTP 200 / HTTP 200 / HTTP 200
```

原配置已备份为 `config.yml.bak-20260927`。

### 这件事的意义（重要）

`docs/deployment-progress.md` 把之前的故障归因为"笔记本必须常开 + 宿舍网 DNS 劫持 53 端口"。**但这次是在笔记本正常开机、网络正常的情况下，隧道照样挂掉的。**

也就是说，**这个架构有两个独立的单点故障**：
1. 机器/网络（你已知）
2. 隧道协议在网络干扰下的脆弱性（你未知）

第二条恰恰**换到云服务器后同样可能发生**（如果机房线路对 UDP 不友好）。所以：

> **迁移到云服务器时，必须把 `protocol: http2` 一起带过去。**

我已经把这条写进 `deploy/cloudflared/config.yml` 模板了 —— 请确认里面有 `protocol: http2` 这一行。

**并且：这次事故说明你需要的不是"换台机器"，而是"宕机可感知"。** 见第八节。

### P0-1　所有内容共用一个 URL，用户无法分享任何一篇文章

**证据**

```javascript
// static/index.html —— 全文件搜索：无 pushState / replaceState / location.hash
```

- 列表页是 `/`，切换板块只改 JS 变量 `activeSection`

- 板块也无法直达：不能把"学术 · 心理学"这个板块的链接发给别人

**为什么这是 P0**

内容型产品的**传播单位是"一篇文章"，不是"一个网站"**。现在用户读到一篇好文章，唯一的分享方式是"你去 inforadar.xin 然后点学术标签再往下翻"——这条传播链等于断了。同理，收藏、稍后读、外部引用全部不可能。

**修法（最小改动版，不用重写）**

```javascript

  activeSection = name;
  if (push) history.pushState({ section: name }, '', '/?s=' + encodeURIComponent(name));
  updateTabsActive();
  loadItems();

window.addEventListener('popstate', e => {
  if (e.state?.section) setSection(e.state.section, false);
});

// 2) 文章可直达
async function openReader(id, push = true) {
  if (push) history.pushState({ item: id }, '', '/a/' + id);
  // ...原有逻辑
}
window.addEventListener('popstate', e => {
  if (e.state?.item) openReader(e.state.item, false); else closeReader();
});
```

**目标形态**（建议一步到位）：`/a/{id}` 是**真正能直接打开**的地址（刷新不 404、能贴到微信/Twitter 有预览卡）。这需要服务端加路由：

```python

    if not item:
        return JSONResponse({"ok": False}, status_code=404)
    return HTMLResponse(render_article_html(item))   # 服务端渲染，见 P0-2
```

### P0-2　首屏 HTML 里没有任何内容，搜索引擎抓到的是"加载中…"

**证据**（线上实测，非推测）

```html
<body>
  ...
  <main id="content"><div class="loading">加载中…</div></main>
  ...
</body>
```

- `<main>` 首屏内容长度：**31 字符**，就是"加载中…"
- `<h2>` 数量：**0**（卡片全部由 JS 在 `fetch` 之后注入）
- 无 `<noscript>` 兜底

配合第一节的元信息全缺（`description` / `og:*` / `canonical` / JSON-LD 全无），结论是：

> **Google/Bing 抓这个站，抓到的是一张空白页。这个站永远不会从搜索获得一个访客。**

对一个资讯聚合站来说，这是最致命的浪费 —— 你辛苦抓来的 180 条内容，对搜索生态完全不可见。

**修法（两条路，按投入选）**

**路线 A（推荐，渐进）**：服务端把首屏内容渲染进 HTML，JS 只负责后续交互。

```python
from fastapi.responses import HTMLResponse

@app.get("/", response_class=HTMLResponse)
def index(s: str = None):
    # 取首屏数据
    sections = [...]                      # 同 /api/sections
    items = db.get_items(section=s, limit=30)
    return HTMLResponse(templates.get_template("index.html").render(
        sections=sections, items=items, active=s))
```

把 `static/index.html` 里的卡片循环改成 Jinja2 模板（`{% for it in items %}`），前端再挂一个"水合"逻辑接管点击。**这是唯一能让 SEO 和分享同时成立的架构。**

**路线 B（更低成本，折中）**：保持 SPA，但至少补齐 `<head>`，让分享有卡片、抓取有摘要。

```html
<meta name="description" content="InfoRadar 聚合 AI 资讯、世界与国内新闻、arXiv 学术论文，只做摘要与原文链接。">
<meta name="robots" content="index,follow">
<link rel="canonical" href="https://inforadar.xin/">
<meta property="og:type" content="website">
<meta property="og:site_name" content="InfoRadar">
<meta property="og:title" content="InfoRadar · 个人资讯雷达">
<meta property="og:description" content="AI 资讯 · 世界新闻 · arXiv 学术，每 4 小时自动更新。">
<meta property="og:url" content="https://inforadar.xin/">
<meta property="og:image" content="https://inforadar.xin/og.png">   <!-- 1200×630，需制作 -->

```

外加三件**必须有、但一个都没有**的基础设施：

| 路径 | 作用 | 现在 |
| --- | --- | --- |
| `/robots.txt` | 告诉爬虫怎么抓 | **404** |
| `/sitemap.xml` | 提交所有文章 URL | **404** |
| `/feed.xml` | 你本身是 RSS 聚合站，却不对外输出 RSS —— 这是最讽刺的缺失 | **404** |

> 补一句：`/feed.xml` 的缺失尤其可惜。RSS 是这个产品的**天然分发渠道**，而且实现成本极低（你已经有了全部数据结构）。任何 RSS 阅读器用户都能订阅你，形成零成本获客。

### P0-3　每板块只留 30 条，超出的内容被永久删除且无归档

**证据**

```yaml
# config.yaml
per_section_keep: 30
```

```python
# app/db.py:161
def trim_section(section, keep):
    """每个板块只保留最新 keep 条（不含搜索结果）。"""
    conn.execute("""DELETE FROM items WHERE section=? AND is_search_result=0
                    AND id NOT IN (SELECT id ... LIMIT ?)""")
```

- 每板块只有 30 条，全站内容上限 = **180 条**
- 超出部分**直接 DELETE，没有归档表、没有冷存储**
- 数据库实测：6 个板块**全部正好 30 条**，即所有板块都长期处于"满载溢出"状态

**用户看到什么**

翻到板块底部，就没有了。没有"加载更多"、没有分页、没有"按日期浏览"、没有归档页。**对资讯站来说，"往期内容"是核心资产**：用户想找上周某篇 AI 新闻，等于找不到。

**修法**

1. 短期：`per_section_keep` 提到 300–500（`fetch_full_content: false` 下摘要很小，180 条才占几百 KB，存 3000 条也无压力）。
2. 中期：`trim_section` 改为 **搬迁而非删除** —— 超过 N 条的老数据进 `items_archive` 表，前台做"归档"页 + 按月份浏览。
3. 配套：列表加分页或无限滚动（现在 `limit` 硬编码 `le=200`，前端固定请求默认 60）。

## 三、P1 问题：安全（我做了可复现验证）

### P1-1　链接协议未校验，恶意 RSS 源可注入可执行链接

**这条我写了复现脚本 `docs/audit/verify_url_risk.py`，不是推测。**

链路三处都没有协议白名单：

```python
# app/crawler.py:28-45 —— 只判 title/link 非空
if not title or not link:
    continue
...
"link": link,          # 原样入库
```

```javascript
// static/index.html:515 —— esc() 只转义引号，不过滤协议
`<a href="${esc(it.link)}" target="_blank" rel="noopener">${esc(it.title)}</a>`
```

实测结果：

```
crawler 放行的用例: 9/9（只判非空，无协议白名单）
确认渲染后仍是可执行伪协议:
  ['javascript 伪协议', 'javascript + 大小写混淆', 'data: URI', 'vbscript:', '前导空白绕过']
引号逃逸（属性注入）: 未发生，esc() 生效     <== 这点做对了
```

注意"前导空白绕过"：`"  javascript:alert(1)"` 会被浏览器忽略首尾空白后**照常执行**。

**攻击面**：任一被聚合的第三方 RSS 源（或其被入侵的 feed）提供上述链接 → 访客点击 → 在 `inforadar.xin` **同源**下执行脚本。同源意味着可以读改站点数据、调用 `/api/update`、读取其他接口。

**修法（服务端落库前 + 前端渲染前，纵深防御）**

```python
# app/crawler.py 顶部
from urllib.parse import urlparse

ALLOWED_SCHEMES = ("http", "https")

def _safe_link(url: str) -> str | None:
    """只放行 http/https，其余（javascript:/data:/vbscript: 等）一律丢弃。"""
    u = (url or "").strip()
    if not u:
        return None
    try:
        scheme = urlparse(u).scheme.lower()
    except ValueError:
        return None
    return u if scheme in ALLOWED_SCHEMES else None
```

```python
# fetch_feed 内
link = _safe_link(e.get("link"))
if not link:
    continue
```

```python
# app/api.py —— 搜索/入库同样过一遍
link = _safe_link(r["url"])
if not link:
    continue
```

```javascript
// static/index.html —— 前端兜底
function safeUrl(u) {
  const s = (u || '').trim();
  return /^https?:\/\//i.test(s) ? s : '';
}
// 渲染时：const href = safeUrl(it.link); href ? `<a href="${esc(href)}">...` : esc(it.title)
```

### P1-3　限流失效点：内存字典不回收、可绕过、可被放大

**证据 a：限流记录永不释放（内存泄漏）**

```python
# app/api.py:31
self._hits = defaultdict(deque)
...
key = (ip, prefix, window)
dq = self._hits[key]
while dq and now - dq[0] > window:
    dq.popleft()
if len(dq) >= limit: ...

```

`defaultdict` 会为**每个 (IP, 路径, 窗口) 组合永久创建一个 key**。公网环境下这是无上限增长。

**证据 b：信任客户端可伪造的头来识别访客**

```python
# app/api.py:38
ip = request.headers.get("cf-connecting-ip") or (
    request.client.host if request.client else "unknown")
```

代码信任 `cf-connecting-ip`，但**没有校验请求是否真的来自 Cloudflare**。当前跑在 `127.0.0.1:7100` 后面有隧道兜着，暂时打不进来；**但只要哪天把 7100 暴露出去（或加了反代），攻击者每次请求换个 `CF-Connecting-IP` 就能无限绕过全部限流**。

**修法**

```python
def _client_ip(request) -> str:
    """只有来自 Cloudflare 的回源才认 CF-Connecting-IP。"""
    peer = request.client.host if request.client else ""
    if peer in CF_IP_RANGES:                      # 校验对端是 CF 回源
        return request.headers.get("cf-connecting-ip") or peer
    return peer
```

```python
# 定期回收空 key，避免无上限增长
if not dq:
    self._hits.pop(key, None)     # 放到 while 之后、append 之前判断
```

**证据 c：Tavily 日限额配错了（我在上一轮提过，这里量化）**

```python
SEARCH_DAILY_GLOBAL = 300   # 全站每日上限
```

账号为 `Researcher` 计划：**1000 次/月**。300 × 30 = 9000，**是月额度的 9 倍**。按设计上限跑，**3.3 天就会打光一个月的额度**，之后所有搜索返回 502。上线公网前必须改成 30 以下。

## 四、P2 问题：内容质量（这是产品的"里子"）

### P2-1　"摘要"其实是字符串截断，不是摘要

**证据**

```python
# app/processor.py:38-66

    head = base[:SUMMARY_MAX]                 # 前 500 字
    for m in re.finditer(r"[。！？.!?]", head):
        if m.start() >= SUMMARY_MIN:          # 再找 300 字后的第一个句号
            cut = m.start() + 1
            break
    summary = head[:cut]                      # 截断
    rest = base[cut:]
    for sent in _split_sentences(rest):       # 再补一句带关键词的句子
        if any(k in sent for k in KEYWORDS) ...
```

**这是"截断 + 补一句"，不是摘要。** 后果：

- 中英混排时截断点会很怪（`SUMMARY_MIN/MAX` 是按字符算的，中文 300 字信息量 ≈ 英文 600 词）
- 摘要经常**不包含结论**，只是文章开头
- `fetch_full_content: false` 时 `base` 退化为 RSS summary，而很多源的 RSS summary 本身就是残缺的 HTML 片段

**修法**：你**已经有一个现成的 LLM 分支**（`app/worddict.py:151 _from_llm`），却只用在点词解释上。把它复用做摘要，收益比点词解释大得多：

```python
# app/processor.py 新增
def make_summary_llm(title, content, rss_summary, llm_cfg):
    """用同一套 OpenAI 兼容接口生成一句话摘要（失败回落规则式）。"""
    prompt = (f"用一句中文概括这条资讯的核心事实，不超过 60 字，只输出摘要本身：\n"
              f"标题：{title}\n正文：{base[:2000]}")
    # ...调用（复用 worddict 里的请求写法），失败 return make_summary(content, rss_summary)
```

建议加缓存并限流（每个 item 只生成一次，落库 `summary` 字段）。**这是投入产出比最高的一处改动**：摘要质量直接决定用户会不会点。

### P2-2　"阅读模式"只对英文内容生效，中文文章在站内读不了

**证据**

```javascript
// static/index.html:497
function isEnglish(text) {
  const letters = (text.match(/[a-zA-Z]/g) || []).length;
  const cjk = (text.match(/[一-鿿]/g) || []).length;
  return letters > 40 && letters > cjk * 2;
}
// :512
const canRead = en && it.id;
```

中文条目**没有"精读"入口**（`canRead` 为 false）。而中文源（中新网 3 个源、雷锋网、极客公园）在你的配置里占了相当比重。

**更麻烦的是**：`fetch_full_content: false` 意味着 `content` 字段基本是空的，阅读模式拿到的只有摘要 —— 所以"精读"这个入口在大多数情况下**点开也只有一段摘要**。实测数据库：204 条里只有 25 条 `content` 非空。

**修法**

- 短期：把"精读"改名为"预览"，或对无 `content` 的条目隐藏该入口（**避免用户点开后失望**）
- 中期：为**允许全文的源**（arXiv 摘要、NPR/TechCrunch 等有明确授权的）单独开全文抓取白名单，让阅读模式真的有内容
- 或者在阅读弹层里做"摘要 + 原文首屏 iframe/预览"，但这涉及版权，需谨慎

### P2-3　时间显示是原始字符串，没有相对时间

```javascript
// :524
<span>${esc(it.published_at || it.fetched_at || '')}</span>
```

直接输出 `2026-09-27 22:47:45`。资讯产品应该显示"3 分钟前 / 2 小时前 / 昨天"——这是**用户判断信息新鲜度的主要线索**。现在用户得自己做减法。

同时 `published_at` 缺失时会落到 `fetched_at`，两者语义不同（发布时间 vs 抓取时间），混在一起展示会**误导用户**认为这是发布时间。

## 五、P3 问题：工程债务（现在不疼，量上来会疼）

### P3-1　抓取和 Web 跑在同一个进程里

```python
# run.py:78
threading.Thread(target=_update_loop, daemon=True).start()
uvicorn.run(app, host="127.0.0.1", port=7100)
```

抓取是**CPU/IO 密集**任务：15 个源 × 20 秒超时、`SequenceMatcher` 摘要去重、SQLite 全表查询。它和 uvicorn 共享 GIL，在 2 核小机器上会**让访客的页面请求明显变慢**。

而且更新状态存在进程内存：

```python
# app/api.py:75
_update_state = {"running": False, "progress": "", "last_error": ""}
```

**进程重启 → 状态丢失 → 可以再触发一次**，两个更新任务并发跑同一个 SQLite。

**修法**：把抓取拆成独立进程/定时器（`systemd timer` + `python update.py`，你已经写好 `update.py` 了！），Web 进程只读数据库。中间用一个 `update_state` 表或文件做状态共享。

### P3-2　每个请求都重新读配置文件和解析 YAML

```python
# app/api.py:84, 114, 169, 186 —— 四处
config = load_config()
```

```python
# app/__init__.py
def load_config():
    with open(CONFIG_PATH, "r", encoding="utf-8") as f:
        return yaml.safe_load(f)
```

每请求一次文件 IO + YAML 解析。改成启动时加载 + `mtime` 变更检测（或加个 `lru_cache`）。

### P3-3　数据层没有迁移机制

```python
# app/db.py:25, 33
CREATE TABLE IF NOT EXISTS sources (...)
CREATE TABLE IF NOT EXISTS items (...)
```

`IF NOT EXISTS` 只能建新表。**一旦你要给 `items` 加字段（比如 P0-1 需要的 `slug`、P2-1 需要的 `summary_source`），老库不会更新，程序会直接报错。** 建议现在就引入最轻量的版本化：

```python
SCHEMA_VERSION = 1
def _migrate(conn):
    v = conn.execute("PRAGMA user_version").fetchone()[0]
    if v < 1:
        conn.execute("ALTER TABLE items ADD COLUMN slug TEXT")
        conn.execute("PRAGMA user_version = 1")
```

顺带：`word_cache` 无上限、`get_recent_titles` 每次更新都对 15 个源做全表扫（`fetched_at` 上有索引但 `is_search_result` 没有），量上来都是成本。

## 六、P4 问题：移动端与可访问性（我按代码逐项核过）

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| **全站无响应式断点** | `@media` 出现次数：**1**，就是 `prefers-reduced-motion` | 手机上布局完全靠 `max-width:880px` 自然收缩，卡片内边距/字号不随屏幕调整 |
| **子板块菜单只认 hover** | `.tab-wrap:hover .dropdown { opacity:1 }`，无 click/focus 触发 | **触屏设备上"新闻""学术"的子板块可能根本点不开**（移动端浏览器对 hover 的处理不一致） |
| **点词弹窗依赖鼠标坐标** | `e.clientX + pad, e.clientY + pad` | 触屏 `click` 的坐标不可靠，弹窗可能飘到屏幕外；英文阅读模式在手机上基本不可用 |
| **可点击元素用 `div`/无 `href` 的 `a`** | `<a onclick="openReader(...)">📖 精读</a>`（无 href） | 键盘不可聚焦、屏幕阅读器不识别为链接、无法中键新标签打开 |
| **无 `role="dialog"` / `aria-modal` / 焦点陷阱** | 三项均无 | 打开阅读弹层后，Tab 键会跑到弹层背后的元素上；关闭后焦点不回归 |
| **Escape 一次键关两层** | `if (e.key === 'Escape') { closeWordPop(); closeReader(); }` | 用户想关掉单词气泡，结果整个阅读器一起关掉 |
| **输入框无 `<label>`** | 只有 `placeholder` | placeholder 一输入就消失，无障碍不达标 |
| **无 `aria-live` 状态播报** | 无 | 搜索完成、更新完成，屏幕阅读器用户完全不知道 |
| **长英文标题不换行** | `.card h2` 无 `overflow-wrap` | 长单词/URL 会撑破卡片（880px 以下尤其明显） |
| **无 `noscript` 兜底** | 无 | JS 失败 = 全站空白 |

## 七、P4 问题：产品定位与合规（这块最容易被技术视角忽略）

### P4-1　标题写着"个人"，形态是"公网匿名站"，两者矛盾

```html
<h1>📡 InfoRadar 个人资讯雷达</h1>
```

`docs/deployment-progress.md` 明确写着"无登录、面向大众免费访问"。那么"个人"两个字是**定位错误**：它让访客不知道这是什么、谁做的、可信度如何。建议改成能表达价值主张的表述（如"AI × 学术 × 时事，一个页面读完"），把"个人"移到 about 页。

### P4-2　一个公网资讯站，没有 about / 免责声明 / 版权说明 / 联系方式

实测这些路由**全部 404**：`/about`、`/privacy`。

**这是真实合规风险**，不只是体验问题。你在聚合 15 个第三方来源的内容：

- 需要说明**内容版权归原作者**、本站只做摘要与索引
- 需要**原文出处署名**（现在卡片有来源 badge，这点好，但没有全局声明）
- 需要**侵权投诉入口**（收到 DMCA/删稿要求时，你连个联系方式都没有）
- 如果以后加分析工具，需要隐私说明

讽刺的是：你的代码里已经体现了很强的版权意识（`fetch_full_content: false`），但**这份意识没有传达给用户和权利人**。补一个静态 `/about` 页成本极低，收益是法律与信任双重保险。

### P4-3　承诺文案与真实行为不一致

```javascript
// :584 —— 兜底文案
'下次更新：' + (sch.next_hint || '每周一、周四 07:00（系统定时任务）')
```

配置里写的是"每 4 小时自动更新"，但前端兜底文案还留着**旧方案（周更）**的残留。而且 `next_hint` 本身是**静态文案**，不是真实计算出的下次更新时间 —— 用户看到的"下次更新"永远只是配置里的一句话。

```javascript
// :507 空状态
'暂无内容，更新由系统定时任务自动执行'
```

现在并没有系统定时任务（是进程内线程），文案与实现不符。

**修法**：`/api/status` 返回**真实计算**的 `next_update_at`（上次成功更新 + `periodic_hours`），前端格式化展示。

### P4-4　没有深浅色、没有字号调节、没有阅读进度

阅读模式做了衬线体、行高 1.9、习语高亮 —— 说明你在意阅读体验。但缺了阅读模式最基础的三件套：**主题切换、字号调节、滚动进度**。这三样的实现成本都不高，但对"精读"场景的价值很直接。

## 八、P5：运维可观测性（本次事故的直接教训）

**事故发生时，你完全不知道。** 我是评审时偶然发现的。这意味着：

如果一个真实用户遇到这个 502，你会在**几天或几周后**才从"网站好像打不开"这类模糊反馈里知道。

**必须补的最小可观测性**：

1. **外部可用性监控**：UptimeRobot（免费版 5 分钟间隔）或 Cloudflare Health Checks，探测 `https://inforadar.xin/api/status`，非 200 立即邮件/Telegram 告警。
2. **内部健康检查**：加一个 `/healthz` 端点，返回 `{db: ok, last_update_hours: 0.4, tunnel: ...}`，比 `/api/status` 更适合给监控用（`/api/status` 返回体太大）。
3. **更新失败告警**：`update_logs.status == 'partial'/'failed'` 时推送通知。**现在"极客公园"已经失败了，你并不知道。**
4. **隧道连接数监控**：`cloudflared` 的 metrics 端点（`127.0.0.1:20241`）暴露连接状态，可以间接判断隧道健康。

## 十、总结：一句话评价

**代码是一个好工程师写的，产品是一个还没想清楚"给谁看、怎么被找到"的人设计的。**

具体来说：

- **工程侧我只挑出一个真正的安全问题**（URL 协议未校验，已验证）和一个隐私问题（搜索词公开）。这两处修起来都是十几行的事 —— 说明地基是好的。
- **产品侧的问题更根本**：没有可分享的 URL、首屏空、没有归档、没有元信息。这四条加起来，等于**这个站只能被"已经知道它的人"手动访问**。它无法自己获得流量，也无法被用户传播。
- **最大的单点风险不是代码，是"你不知道站挂了"**。这次事故在评审过程中真实发生，而且是在机器正常开机的情况下 —— 这比"笔记本要常开"更值得你警惕。

**如果只能做三件事**：① 补 `<head>` + `robots.txt` + `sitemap.xml` + `feed.xml`（半天）；② 做 `/a/{id}` 服务端渲染的文章页（2–3 天）；③ 接入 UptimeRobot（10 分钟）。做完这三件，这个站才第一次具备"活着"和"被找到"的属性。
